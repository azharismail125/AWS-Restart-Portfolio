3D E-Commerce Platform Architecture

This document covers the cloud architecture for a 3D e-commerce web application. The platform lets users view and interact with 3D product models — furniture, gadgets, and fashion items — before buying them online.

1. AWS Service Choices

Amazon S3 is the primary storage for static assets and 3D model files. When a seller uploads a model, S3 fires an event to trigger backend processing. Public access is blocked to prevent unauthorized access and reduce exposure to the internet.

Amazon CloudFront is a Content Delivery Network that caches 3D assets at edge locations globally. This reduces repeated origin requests and keeps load times fast for users regardless of where they are situated.

EC2 with AWS Lambda: EC2 runs continuously for core backend work — session management, cart operations, and checkouts — across multiple Availability Zones. Lambda handles stateless, event-driven tasks such as image processing or file validation, which is useful when workloads spike unexpectedly.

RDS instead of DynamoDB: RDS handles transactional relational data — inventory, orders, customer records — where strict data integrity matters. DynamoDB was considered but RDS is a better fit for complex, relational inventory and order systems.

Elastic Load Balancer (ELB): The Application Load Balancer distributes dynamic traffic across healthy EC2 instances using continuous health checks, and accounts for rapid increases or decreases in traffic.

Amazon Route 53 handles DNS and domain routing. It performs health checks and fails over to backup resources automatically if a primary component goes down.

CloudWatch & Trusted Advisor: CloudWatch tracks application health, EC2 utilization under heavy 3D rendering load, and Lambda invocations. Trusted Advisor flags opportunities to improve performance, security, and cost efficiency across the AWS environment.

2. Meeting the 5 Key Requirements

High Availability: Multi-AZ EC2 deployment means a single data center outage won't drop active shopping sessions. Route 53 and the Application Load Balancer only route traffic to healthy instances.

Scalability: Auto Scaling adjusts the EC2 fleet based on demand. CloudFront handles delivery of large 3D assets globally without adding load on the backend.

Performance: Caching 3D content at CloudFront edge locations means fast page loads and smooth rendering regardless of the user's location.

Security: The backend sits in a VPC with private subnets so there's no direct internet exposure. S3 buckets are private, accessed only through CloudFront. AWS WAF filters malicious traffic, Security Groups restrict inbound access, and IAM policies control who can alter resources.

Cost Optimization: Lambda handles intermittent model processing to avoid idle EC2 costs. Auto Scaling uses minimum and maximum thresholds to prevent over-provisioning during both quiet and peak periods.

3. Design Trade-offs & Challenges

EC2 and Lambda: EC2 handles continuous sessions reliably but requires active capacity planning. Lambda drops server management overhead for 3D model processing but brings cold starts and potential latency during first-time requests.

Performance and Cost: Intense caching, extra compute, or provisioned concurrency can improve responsiveness but will also raise spend and configuration complexity.

Simplicity vs Resilience: Multi-Availability Zone and load-balanced infrastructure prevents downtime but costs more and is more complex to manage than a single-server setup.

Public vs. Private Origin: Keeping the ALB private behind CloudFront shields the backend from unwanted direct internet exposure but requires more VPC work — NAT gateways, routing rules, and careful security boundary design.

Scaling Dependencies: A sudden spike from a popular product launch triggers rapid Auto Scaling, which can create connection pressure on downstream components like RDS. System-wide monitoring is needed to detect and mitigate these bottlenecks before customers notice.
